What IDOR Actually Is

Before you can hunt it, you need a precise mental model. Most "IDOR tutorials" stop at "change ?id=1 to ?id=2." Real-world IDOR is broader, sneakier, and more lucrative.

→The definition that matters

An Insecure Direct Object Reference is any access-control failure where a user-controlled identifier — in a URL path, query string, body, header, cookie, or GraphQL variable — references a backend object, and the server returns or modifies that object without verifying that the requesting user is allowed to touch it.

Crucially: IDOR is an authorization failure, not an authentication failure. The attacker is usually authenticated. The bug is that the server checked "are you logged in?" but forgot to check "are you this user?"

// Mental model

Every request that touches a database row or filesystem object is a question. Authentication answers who is asking. Authorization answers are they allowed to ask this particular question. IDOR is a server that forgets to ask the second question.

→Horizontal vs. vertical

Two flavors, very different impact:

// IDOR · Two Privilege Directions
Horizontal
Same role, different victim

You're a regular user. You access another regular user's data. Most common; usually Medium-to-High depending on data sensitivity.

user_A  →  reads  →  user_B's invoices
Vertical
Lower role, higher-privilege function

You're a regular user. You hit an admin-only endpoint by manipulating IDs or routes. Almost always High-to-Critical.

user_A  →  calls  →  /admin/deleteUser/123

→Where it actually lives in OWASP

IDOR sits at #1 in both lists that matter. In the OWASP Top 10:2025 (released as RC1 in November 2025 and the current published edition), it falls under A01:2025 — Broken Access Control, the same position it held in 2021. The 2025 edition's notable change here is that SSRF was rolled into A01 — recognizing that server-side request forgery is just another flavor of "the server fetched something on behalf of a user without checking whether they were allowed to ask for it."

In the OWASP API Security Top 10 (2023 — still the current edition as of mid-2026), IDOR is renamed BOLA — Broken Object Level Authorization, and it remains API1. The rename matters: it shifts the framing from "the ID was guessable" to "the authorization check was missing," which is what the bug actually is. Treat these two lists as the same problem class through different vocabulary.

// OWASP Top 10:2025 · the full lineup

Released as RC1 on 6 Nov 2025. The current ranking: A01 Broken Access Control (SSRF now folded in), A02 Security Misconfiguration, A03 Software Supply Chain Failures (new), A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging & Alerting Failures, and A10 Mishandling of Exceptional Conditions (new). There's also an honorable-mention entry, X03:2025 Inappropriate Trust in AI Generated Code ("vibe coding") — relevant in section 08 below.

// Why programs pay for it

IDOR is a server-side bug with zero user interaction, a working PoC fits in a single HTTP request, and the impact (PII exposure, account takeover, tenant isolation breach) is easy to demonstrate. Triage teams love it; that's why even "boring" horizontal IDOR routinely pays four figures and chained criticals hit five.

→IDOR vs BOLA vs BOPLA vs BFLA

"IDOR" is the classic web-app term. The OWASP API Security Top 10:2023 split the same idea into three sharper categories, and knowing which one you've found makes your report land faster and stops triagers from downgrading it. Learn to name the exact shape:

NameWhat's unprotectedConcrete example
BOLA API1:2023 The object as a whole — "can I touch this record?" GET /invoices/1002 returns another user's invoice. This is "IDOR" in the classic sense.
BOPLA API3:2023 Individual properties/fields — "can I read or set this field?" Response leaks a hidden ssn field (excessive data exposure); or your PATCH body sets role: "admin" and the server accepts it (mass assignment).
BFLA API5:2023 The function/endpoint — "am I allowed to call this at all?" A regular user calls DELETE /admin/users/42. This is vertical IDOR's API-shaped name.
// One acronym worth remembering

BOPLA (API3:2023) is a merger of two older 2019 categories — Excessive Data Exposure (the API returns fields you shouldn't see) and Mass Assignment (the API accepts fields you shouldn't set). Both are property-level authorization failures, which is why they now live under one name. OWASP writes it out as "Broken Object Property Level Authorization"; "BOPLA" is community shorthand. See section 06 for mass-assignment hunting.

→The one anti-pattern behind all of them

Every format in this guide — sequential integers, UUIDs, MongoDB ObjectIDs, hashids — fails the same way: the application treats knowledge of an identifier as proof of authorization. "You knew the ID, so you must be allowed to have it." That's the whole bug. No identifier format, however random, fixes a missing server-side ownership check — randomness only changes how hard the ID is to obtain, never whether the check exists.

// The standard says so out loud

RFC 9562 (May 2024, the current UUID specification) states plainly in §6.9 that UUIDs "do not guarantee uniqueness, and MUST NOT be used as security capabilities" — i.e. an unguessable ID is not an access-control mechanism. When a program says "but the ID is a random UUID, so it's not exploitable," this is your citation: the spec authors themselves say don't rely on that.

→The CWE map (for your reports)

Cite the right weakness ID and your triager can classify the report in one read:

→Impact menu

  • Read — view another user's PII, invoices, messages, files, internal notes
  • Update — change another user's email, password, role, payment method (frequently leads to ATO)
  • Delete — destroy other users' resources, irrecoverably in some apps
  • Create on someone else's account — plant data, files, comments, transactions
  • Cross-tenant breach — in SaaS apps, read or modify data belonging to a different customer organization (almost always Critical)

Recon & Target Selection

IDORs are an authorization-logic class — they only appear where there's data to access. Your recon job is to find the data-shaped surface area as fast as possible.

→Picking a program

Not all programs are equal. For IDOR hunting specifically, prefer:

  • Apps with multi-tenant or per-user data — CRMs, project trackers, healthcare portals, banking, e-commerce, BI dashboards, file-sharing
  • Apps with rich API surface — REST/GraphQL/internal APIs visible to authenticated users
  • Apps that allow you to create two accounts — same plan, same org, ideally different orgs/tenants
  • Newer programs or recently-shipped features — check the program's "recently launched" or "scope changes" log
// Scope discipline

Re-read the scope every time you switch targets. "All subdomains of *.example.com" rarely includes support.example.com if it's run by a vendor. Out-of-scope IDORs waste your time and the program's. Some programs explicitly exclude IDORs on "self-service" features (e.g. team-member endpoints where multi-user access is intentional).

→Mapping the data surface

You want to discover every endpoint the app exposes — especially the ones the official frontend doesn't use anymore.

  1. Spider with two browsers. Two profiles (or browsers) authenticated as two different users. Burp Suite recording in the background. Click everything in both accounts.
  2. Pull every JavaScript bundle. Use getJS, katana, or a Burp extension to enumerate .js files, then run LinkFinder / SecretFinder / jsluice over them to extract endpoints, parameter names, internal API hostnames, and AWS-style identifiers.
  3. Hit common API doc paths. /swagger, /swagger-ui, /api-docs, /openapi.json, /v2/api-docs, /graphql, /graphiql, /altair, /playground, /redoc. A leaked Swagger spec is an IDOR map.
  4. Search archived versions. web.archive.org and Common Crawl frequently expose old endpoints that the current frontend doesn't link to but the backend still serves.
  5. Wordlist-fuzz hidden endpoints. ffuf or feroxbuster with SecLists' API wordlists (api/objects.txt, api/api-endpoints.txt), then narrow on 401/403/200 anomalies.
  6. Check mobile. Decompile the Android APK (apktool d app.apk) and grep for base URLs and endpoint strings. Mobile clients routinely use endpoints the web app no longer references but which still ship full responses.

→Mine the source maps (the highest-ROI recon trick)

Modern SPAs ship minified JavaScript, but many also ship the .js.map source maps next to it — the files browser devtools use to show original source while debugging. Left in production (extremely common), a source map hands you the app's original, un-minified source tree: every fetch() call site, internal endpoint path, parameter name, feature flag, and sometimes hardcoded config. Look for //# sourceMappingURL= at the bottom of each bundle, or just append .map to the bundle URL and see if it 200s.

Reconstruct the original source from a bundleRECON
# Go: auto-detects sourceMappingURL, rebuilds the source tree
sourcemapper -url https://target.com/static/js/main.abc123.js -output ./src

# Python: --detect crawls the page's <script> tags and pulls every .map it finds
unwebpack-sourcemap.py --detect https://target.com/ ./src

# then grep the recovered source for the IDOR-shaped surface
grep -rEho "/api/[a-zA-Z0-9/_{}.-]+" ./src | sort -u
grep -rEon "[a-zA-Z_]+(Id|_id|Uuid|Token|Key)" ./src | sort -u

→A copy-paste recon pass

A fast, repeatable sweep to enumerate the data-shaped surface. Scope every command to authorized targets only.

Endpoint & parameter enumerationRECON
# 1. Every historical URL ever archived (Wayback, CommonCrawl, OTX, URLScan)
gau target.com | tee all-urls.txt
waymore -i target.com -mode U            # -mode R also downloads archived response BODIES

# 2. Crawl live + classify the API surface (REST / GraphQL / SOAP)
katana -u https://target.com -jc -kf all -kb-endpoints -o katana.txt

# 3. Extract endpoints & secrets from JS with a real parser (not regex)
cat js-urls.txt | jsluice urls | jq -r .url | sort -u

# 4. Discover hidden ID-bearing parameters the UI never shows
arjun -u https://target.com/api/v2/account -m GET,POST-JSON

# 5. Probe common API-doc & schema paths
ffuf -u https://target.com/FUZZ -w swagger-paths.txt \
  -mc 200,401,403 -fs 0    # /swagger.json /openapi.json /graphql /v2/api-docs …
// Where API maps love to hide

Beyond /swagger and /graphql: leaked Postman collections (search postman.com for the brand), .well-known/ manifests, exposed /actuator/mappings (Spring Boot), /api/v*/schema (DRF), CI artifacts, and *.har files committed to public repos. Each one is a pre-built list of every ID-bearing endpoint the developers use.

// Pro tip — recently-shipped features

The newer the feature, the higher the IDOR probability. Watch the app's changelog, blog, release notes, and Twitter/X account. When a vendor announces "we just shipped team invites" — within 48 hours, hit every endpoint of that flow with two accounts.

Identifying IDOR Candidates

Once you've mapped endpoints, your job is to identify which request parameters look like object references. Train your eye to spot identifiers wherever they're hiding — they aren't always called id.

→Where IDs hide

LocationExamplesNotes
URL path/users/42/profileMost obvious
Query string?orderId=9011Easy to enumerate
Request body{"target_user": 42}Often missed

→ID format guide

The format of the identifier shapes how you attack it. The column that matters most is "predictable portion" — the part an attacker doesn't have to guess. Ordered roughly from easiest to hardest:

FormatExamplePredictable portion & attack
Sequential int 1, 2, 3, … 9847 100%. Enumerate freely — Intruder Numbers or Turbo Intruder. Highest visible ID also leaks total record count.
Base64 int / JSON SW52b2ljZToxMDQy 0 bits of security — reversible encoding, not encryption. Decode, enumerate, re-encode (see below).
Hashids / Sqids NkK9dwLl2 Reversible obfuscation, not a hash. Leaked salt+alphabet ⇒ decode every ID. See the callout below.
MongoDB ObjectID 507f191e810c19729de860ea Only ~24 bits truly vary per process. One known same-process ID collapses the rest. Deep-dive below.
UUIDv1 (time+MAC) 6ba7b810-9dad-11d1-… Timestamp + constant MAC/clock_seq. The sandwich attack brute-forces the timestamp window. Deep-dive below.
Snowflake (Twitter/Discord) 175928847299117063 ms timestamp + small worker/sequence bits. Public decoders exist; narrow to a few thousand candidates in a time window.
UUIDv7 / ULID / KSUID 018f7a1c-3e4b-7d21-… 48-bit ms timestamp is non-secret; 62–128 random bits remain. Not enumerable, but never use for secret tokens.
Hash-shaped (MD5/SHA-1) 5d41402abc4b2a76… Often md5(user_id) or md5(email). Hash your own known values; try common inputs.
Slug / username /u/alice-johnson Enumerate from OSINT, comments, mentions, member lists, @-handles.
UUIDv4 / nanoid / Stripe f47ac10b-58cc-4372-… 119–126 random bits. Direct enumeration is hopeless — hunt for leaks instead (next subsection).
// Read the version nibble

For any UUID, the first character of the third group is the version: …-1xxx-… is time-based (attackable), …-4xxx-… is random, …-7xxx-… is timestamp-ordered. A 1 or 7 there is a signal to keep digging; a 4 means pivot to leak-hunting.

MongoDB ObjectID — why "random-looking" isn't random

An ObjectID looks like 12 random bytes. It isn't. Per the current spec it's 4-byte timestamp + 5-byte per-process value + 3-byte counter:

507f191e810c19729de860ea — decomposedDECODE
507f191e  # 4 bytes — unix timestamp (seconds). NOT secret: you know ~when a record was made.
810c19729d # 5 bytes — random per PROCESS. Constant for the whole server-process lifetime!
e860ea    # 3 bytes — counter, +1 per ObjectID the process mints.

The trap: the 5-byte "random" middle is generated once when the process starts, not per document. So if you can grab any single ObjectID from the same server process — your own account's ID, one leaked in a response or error — you now know those 40 bits for every ObjectID that process creates. That leaves only a narrow timestamp window and a small counter delta to brute-force, turning a nominal 96-bit space into roughly 10³–10⁶ candidates. andresriancho/mongo-objectid-predict automates exactly this.

UUIDv1 & the sandwich attack

A UUIDv1 is a 60-bit timestamp (100 ns ticks) + a clock sequence + the generator's 48-bit MAC address. The MAC is constant, and many libraries fix the clock sequence per process — so the only thing that changes between two UUIDs from the same server is the timestamp. The sandwich attack exploits this on flows where you can trigger UUID generation (e.g. password-reset tokens):

  1. Request a reset for your account → capture UUID T1 (the "bottom slice").
  2. Request a reset for the victim (or wait for their action) → their token is minted between your two requests.
  3. Immediately request another reset for your account → capture UUID T2 (the "top slice").
  4. Every valid timestamp lies between T1 and T2. Regenerate candidate UUIDs across that window and brute-force the reset link.

Tools that do the regeneration: guidtool, crazycat256/uuidtool, and Lupin-Holmes/sandwich. This turned several 2024–2025 password-reset flows into full account takeovers.

// Hashids and Sqids are NOT encryption

Hashids (and its 2023 successor Sqids) encode integers into short strings like NkK9dwLl2. Their own maintainers say it outright: "Do not use this as a security measure… Hashids is not an encryption library." The "salt" is not a cryptographic secret — it just permutes the alphabet, and it's routinely hardcoded in client-side JS or public repos. Recover the salt+alphabet (or brute a short salt against one known plaintext/ciphertext pair) and you can decode every ID the app will ever issue — collapsing it straight back to sequential integers.

Decode before you dismiss

An opaque-looking token is often just an encoding. Before assuming an ID is unguessable, run it through the obvious decoders:

Is it actually random, or just wrapped?DECODE
# Base64 — GraphQL Relay global IDs love this shape
echo 'SW52b2ljZToxMDQy' | base64 -d      # → "Invoice:1042"  ⇒ try Invoice:1043

# JWT — the payload is only base64, readable by anyone holding the token
echo '<jwt>' | cut -d. -f2 | base64 -d       # reveals sub / tenant_id / role claims
jwt_tool <jwt> -T                          # tamper claims; test alg:none & weak-secret

# Snowflake / ObjectID — decode the embedded timestamp to confirm the format
// Don't forget the header IDs

Object references also live in ETag and Last-Modified headers. Apache's default FileETag encodes the file's inode, size and mtime; a leaked Last-Modified gives you the exact creation timestamp you need to narrow a UUIDv1/Snowflake/ObjectID window elsewhere in the same app.

→Hunting "unguessable" IDs

UUIDv4 doesn't kill IDOR — it just moves the bug. The identifier still has to reach the attacker somehow. Look here:

  • Public-facing lists — comment threads, "members of this org" pages, "people who liked this," activity feeds — these routinely leak UUIDs the app considers private
  • Search endpoints — /api/search?q=alice often returns the UUID alongside the displayname
  • Old API versions — /api/v1/users may still return a full enumerable list when /v2/ doesn't
  • Webhooks and notifications — outbound notifications (Slack, email, mobile push) sometimes contain raw object IDs
  • Referer headers — when a user clicks a link out of your app, their object ID can leak in the Referer to an attacker-controlled URL
  • Error messages — verbose JSON errors sometimes echo back a target ID you weren't authorized to know
// Real-world · Aug 2024

A researcher reported an IDOR exposing 500,000+ US passport scans in a government-adjacent submission portal. The "identifier" was a sequential integer (id=4550381), and a sibling endpoint /api/v1/attachment-list?enamemId=... let an attacker enumerate file IDs per user. The fundamentals didn't change in twenty years — only the size of the database behind them.

// 03 · Hunting

Testing Methodology

A disciplined two-account workflow with Burp Suite (or Caido) is the foundation of IDOR hunting. This is the loop you should be able to execute in your sleep.

→The two-account loop

  1. Create two accounts. Account A is the "attacker"; Account B is the "victim." Same plan/tenant ideally, but also test cross-tenant if the app supports it.
  2. Populate both accounts with distinguishable data. Different names, different uploads, different settings. Visible differences = easier confirmation.
  3. Use Account B normally. Walk through every feature. Capture every request in Burp's history.
  4. Now swap into Account A's session. Replay Account B's requests with Account A's cookies / tokens.
  5. Confirm. A successful IDOR returns Account B's data while authenticated as Account A.

→The Match & Replace shortcut

Manually swapping cookies for every request is slow. Configure Burp's Match & Replace rules to auto-swap session tokens on the fly:

Burp Suite → Proxy → Match & Replace CONFIG 
Type:    Request header
Match:   ^Authorization:.*$
Replace: Authorization: Bearer eyJhbGciOi...<ACCOUNT_A_TOKEN>
☑ Regex match    ☑ Enabled

Now you can browse as Account B and Burp will rewrite requests on the fly to be authenticated as Account A — and you watch which responses still return Account B's data. The Autorize extension automates exactly this loop.

→Autorize / AuthMatrix

Autorize (Burp/Caido) is the canonical IDOR-hunting extension. Workflow:

  1. Sign in as Account A, copy Account A's session token, paste into Autorize's "Configuration" tab.
  2. Switch session to Account B, browse the app.
  3. Autorize replays every request a second time with Account A's token and a third time unauthenticated.
  4. Color-coded results: Bypassed! means Account A's response matched B's — you've potentially found an IDOR. Enforced! means access was blocked.
// False positives

Autorize compares response sizes/contents. "Bypassed" can fire on innocuous responses (e.g. generic 404 pages, public endpoints). Always manually verify the response actually contains victim data before reporting.

Pick the right tool for the job — they are not interchangeable:

ToolModelBest for
Autorize (Burp)Auto-replays each request under a low-priv session + unauth; 3-way compare.Fast passive sweep while you browse. Your default.
Auth Analyzer (Burp)Extracts & substitutes session tokens across N configured sessions in parallel.Apps with 3+ roles, or CSRF-token/session refresh that Autorize chokes on.
AuthMatrix (Burp)Manual users × roles × requests grid you populate and re-run.Structured, repeatable regression across a whole role matrix.
Caido pluginscaido-community/autorize, /authmatrix, /authswap.Same workflows if Caido is your primary proxy — all actively maintained.
// Always test three identities, not two

For every request, compare the response as (1) the owner, (2) a different authenticated user, and (3) fully unauthenticated (strip the cookie/token entirely). The third case catches endpoints that never check auth at all — the easiest, highest-severity IDORs — and they're the ones a strict two-account loop can miss.

→The minimum viable test request

What a vulnerable request/response pair looks like in practice:

Account B's legitimate request GET 
GET /api/v2/users/7011/invoices HTTP/2
Host: api.target.com
Authorization: Bearer <B's token>
Accept: application/json
Attacker request — same URL, A's token GET 
GET /api/v2/users/7011/invoices HTTP/2
Host: api.target.com
Authorization: Bearer <A's token>
Accept: application/json

# If response returns B's invoices ⇒ IDOR confirmed

→Don't just test GET

The fastest way to leave money on the table is testing only read endpoints. The same identifier flowing through POST, PUT, PATCH, or DELETE often has different (or absent) authorization. Always re-test every parameter against every method the server accepts:

Per-endpoint method matrix
  • GET — does it leak victim data?
  • POST — can you create resources under the victim's account?
  • PUT / PATCH — can you mutate victim fields (email, password reset token, role)?
  • DELETE — can you delete victim's resources?
  • OPTIONS — does the CORS preflight reveal allowed methods you didn't see in the UI?

→Blind IDOR — when the response says nothing

Not every IDOR echoes the victim's data back. A PATCH or DELETE often returns a bland 200 {"success": true} whether or not it touched a foreign object. This is blind IDOR, and you confirm it by observing the side effect, not the response:

  • Cross-check from the victim account. Fire the mutation as Account A against B's object, then log into B and confirm the change landed.
  • Watch an out-of-band signal. Did the victim get a notification email? Did a webhook fire? Did an audit-log entry appear?
  • Diff the timing / status. A real object often returns 200/204; a non-existent one 404. That difference alone is an existence oracle even when content is identical.
// Verify like a triager will

Before you write it up, run the swap-and-revert: perform the action cross-account, confirm the effect, then undo it. Capture both accounts' state at each step. A finding you can toggle on and off on demand is one no triager can call a coincidence — and it's the difference between "informative" and "paid."

Bypass Techniques

When the obvious test returns 403, you're not done — you've just found that one code path checks authorization. There are usually others. Below: the modern bypass catalog that still pays in 2025.

→HTTP verb tampering

Many frameworks register handlers per-method. A team that hardened GET /api/users/:id may have left POST, PUT, PATCH, HEAD, or even bogus methods (FOO) wide open. Try:

HTTP method tamperingFUZZ
GET     /api/users/7011/email    → 403
POST    /api/users/7011/email    → 200  # sometimes
PUT     /api/users/7011/email    → 200  # common
PATCH   /api/users/7011/email    → 200
HEAD    /api/users/7011/email    → 200  # headers only, but reveals existence
FOO     /api/users/7011/email    → 200  # frameworks that fall through to GET

→Path normalization tricks

If the auth check is path-based and the application server normalizes paths differently than the WAF or proxy, you can sometimes slip an unauthorized request past the check. Try every variant — modern routers/proxies disagree on which to normalize:

VariantPath
Baseline/api/users/7011
Trailing slash/api/users/7011/
Double slash/api//users/7011
Dot-segment/api/./users/7011
Parent traversal/api/users/7000/../7011
Encoded slash/api/users%2F7011
Double-encoded/api/users%252F7011
Encoded null/api/users/7011%00
Unicode space/api/users/7011%20
Path parameter/api/users/7011;.json
Extension swap/api/users/7011.json, .xml, .html

→Header-based bypass

Reverse proxies and WAFs sometimes rewrite the request URL based on headers — and authorization middleware sometimes runs against the rewritten URL while the application handler runs against the original. Try injecting:

Headers worth testingHEADERS

X-Rewrite-URL: /api/users/7011
X-Forwarded-For: 127.0.0.1

→Parameter pollution & wrapping

Some servers parse the first occurrence of a parameter; others the last. WAFs may inspect one while application code reads the other. Try every combination:

Parameter pollution variantsPOLLUTE
# Two values of the same parameter
GET /api/invoice?id=SELF&id=7011
GET /api/invoice?id=7011&id=SELF

# Array wrapping (JSON body)
{"user_id": 7011}            → 403
{"user_id": [7011]}          → 200  # auth check on int, app reads array[0]
{"user_id": ["SELF", 7011]}  → 200
{"user_id": {"value": 7011}}  → 200  # auth on primitive, app on object

# Type confusion
{"user_id": "7011"}          # string vs int
{"user_id": 7011.0}            # float vs int
{"user_id": "007011"}          # leading zeros
{"user_id": 0x1B63}            # hex

→JSON / XML / form-encoded swap

Many APIs accept multiple content types. The deserializer for one format may apply different validation than another. Try resending the same logical request as:

  • application/json  →  application/xml
  • application/json  →  application/x-www-form-urlencoded
  • application/json  →  multipart/form-data
  • application/json  →  text/xml (legacy XML parsers occasionally still work)

→Endpoint variants

For any sensitive operation, the developer often shipped multiple endpoints over time. Try every guess:

  • Version downgrade — /api/v3/users/7011 blocked but /api/v2/, /api/v1/, /api/internal/, /api/legacy/ still alive
  • Mobile-only endpoints — /api/mobile/, /api/ios/, /api/android/ with looser auth
  • Subpath variants — if /users/7011/profile blocks, try /users/7011/details, /users/7011/info, /users/7011/summary
  • List endpoints — when fetching /users/7011 403s, try /users?ids=7011 or /users/batch?ids[]=7011
  • Export / report endpoints — /export, /print, /pdf, /download often skip the in-app auth layer

→Send the ID in two places at once

A classic, still-paying bypass: the authorization middleware checks the ID in one location while the application handler reads it from another. Put your own ID where the check looks, and the victim's ID where the code actually reads. Try every pairing:

Location-mismatch bypassFUZZ
# Auth check reads the path (SELF); handler trusts the body (victim)
POST /api/users/SELF/update
{"user_id": 7011, "email": "attacker@evil.com"}

# Auth check reads the query; handler trusts the JSON
POST /api/invoice?id=SELF
{"id": 7011}

# Header vs body — common in multi-tenant SaaS
X-Account-Id: SELF
{"account_id": 7011}

→Read the response codes as an oracle

The difference between rejections tells you which control you're up against — and where to push:

// Modern winner — Unicode & whitespace

Several 2024-2025 writeups documented bypasses using zero-width Unicode characters or trailing whitespace in path segments — /api/users/7011%E2%80%8B (zero-width space) or /api/users/%097011 (tab character). The router strips them and routes the request; the WAF and auth middleware see a different path and let it through.

// 05 · Hunting

GraphQL IDOR

GraphQL changes IDOR from "is one route protected?" to "is every resolver protected?" — and the answer is almost never. Plus aliasing turns a single HTTP request into hundreds of authorization probes.

→Step one — introspection

If introspection is on, you have the entire API map for free. Always check:

Standard introspection queryPOST
POST /graphql HTTP/2
Content-Type: application/json

{"query": "{ __schema { types { name fields { name args { name type { name } } } } } }"}

Introspection disabled? It's hidden, not gone. Two moves recover most of it:

  • Fingerprint the engine first. graphw00f identifies the server implementation (Apollo, Hasura, graphql-java, Yoga…) from its error-handling quirks, then cross-references the GraphQL Threat Matrix to tell you which defenses that engine ships by default and its known CVEs. Now you know what to expect.
  • Recover the schema from typo hints. Most servers answer a wrong field name with "Did you mean … ?". Clairvoyance brute-forces near-miss names, harvests those suggestions, and rebuilds the schema field-by-field — with introspection fully off. (Mitigation on the defender side is blockFieldSuggestions; when it's absent, this works.)

→Field-level authorization gaps

Even when query.user enforces "you must be that user," nested fields (user.orders, user.paymentMethods) are separate resolvers. Developers often guard the top level and forget the leaves.

Direct access — blockedPOST
query {
  user(id: 7011) {
    email
    # → "Unauthorized"
  }
}
Nested access — leaksPOST
query {
  organization(id: 9) {
    members {
      id
      email          # leaks all members
      paymentMethod  # even worse
    }
  }
}

→The Relay node() back door

Schemas built on the Relay spec expose a generic node(id: ID!) query that returns any object implementing the Node interface. Developers often lock down the named query (user(id)) but forget that node() resolves to the same object through a different door — and the global ID is usually just base64("User:7011"). If the guarded query 403s, try the generic one:

Same object, unguarded pathPOST
query {
  node(id: "VXNlcjo3MDEx") {   # base64("User:7011")
    ... on User { email phone }
  }
}

This exact class was assigned CVEs in 2025 (e.g. API Platform's auto-generated node resolver). The lesson generalizes: enumerate every path that reaches an object, not just the one your client SDK uses.

→Directive deception (fragment bypass)

Custom auth directives like @auth are enforced by middleware that walks the query's syntax tree. Some implementations only check directives on fields written directly in the query and never recurse into fragments. Request the same protected field through an inline or named fragment and the check can be silently skipped:

Route the field through a fragmentPOST
query {
  me {
    ...leak            # the @auth walker may never visit this node
  }
}
fragment leak on User { ssn internalNotes apiKey }

Always test protected fields three ways — inline in the query, via an inline fragment (... on Type), and via a named fragment spread — because they are not guaranteed to be authorized identically.

→Alias-batched IDOR & rate-limit bypass

This is the GraphQL primitive that turned modest IDORs into critical mass-extraction bugs. Aliases let you call the same resolver many times in a single HTTP request. Most rate limiters and lockouts count requests, not resolver invocations.

Alias-batched user enumerationPOST
query BatchExfil {
  u1: user(id: 7001) { id email phone createdAt }
  u2: user(id: 7002) { id email phone createdAt }
  u3: user(id: 7003) { id email phone createdAt }
  // ... up to several hundred aliases ...
  u200: user(id: 7200) { id email phone createdAt }
}

# One HTTP request → 200 user records returned
# Rate limiter sees: 1 request. WAF sees: 1 request.

The same primitive applies to:

  • Authentication brute-force — 100 password candidates in a single POST against a login(email, password) mutation
  • OTP/token brute-force — 50 OTP guesses per request against verifyCode(code)
  • Coupon enumeration — short-entropy codes batched through validateCoupon(code)
  • Hidden field probing — alias-call an admin mutation 20 ways to detect resolver-level authorization gaps
// Disclosed pattern · alias batching

Multiple HackerOne reports (incl. #1016122, #1987489) documented programs where alias batching turned per-request rate limits into nominal protection — 100 OTP guesses per request hit the right code before any lockout fired. Modern GraphQL servers should rate-limit at the operation level; many still don't.

→Batched-operations IDOR

Separate from aliasing, GraphQL also supports sending an array of operations in one request. Same effect, different shape:

Operation batchingPOST
[
  {"query": "{ user(id: 7001) { email } }"},
  {"query": "{ user(id: 7002) { email } }"},
  {"query": "{ user(id: 7003) { email } }"}
]

→Mutation IDOR

Read-side IDOR is the obvious case; mutations are where the money lives. Mutations that take a target ID — updateUser, resetPassword, transferOwnership, deleteOrganization, setRole — should be your top priority once introspection succeeds.

// "Persisted queries" ≠ a wall

If a target uses persisted queries, find out which kind. Automatic Persisted Queries (APQ) are a bandwidth optimization — the client can still register and run any new query; the GraphQL Yoga docs say it outright: "APQ do not provide any security features." Every technique above still applies. Only a true safelist / persisted-query list (PQL) — a fixed allowlist that rejects unknown queries — narrows the surface, and even then an allowlisted query with an ID argument can still be IDOR-vulnerable.

GraphQL IDOR checklist
  • Fingerprint + schema — graphw00f the engine; if introspection is off, recover with Clairvoyance
  • Per-query auth — every Query.X with an ID argument tested for horizontal IDOR
  • Nested resolvers — every traversal through relationships re-tested independently
  • The node() back door — retry any blocked object through the generic Relay node(id) query
  • Fragments — protected fields re-requested via inline & named fragments (directive deception)
  • Aliasing — does sending 50 aliases of the same field execute 50 times?
  • Mutations — every Mutation.X taking a target ID tested with a foreign ID
  • Hidden / admin mutations — does a low-privilege session call an admin mutation and get a response other than auth-error?
  • Field-level auth — sensitive fields (ssn, internalNotes, apiKey) requested via a permitted path
// 06 · Advanced

Advanced Techniques

Past the basics, the highest-paying IDORs come from chaining and from non-obvious attack surfaces. This is what separates "another invoice IDOR" from a $20K bounty.

→Chaining for impact

A medium IDOR plus another medium bug often equals a critical. Chains worth building:

  • IDOR → ATO. Find an IDOR on the password-reset flow or email-change flow. Update victim's email to one you control, trigger a reset, take over.
  • IDOR + IDOR. The first IDOR leaks the second IDOR's required identifier (e.g. the API key, the UUID, the reset token).
  • IDOR + verbose error. An "unauthorized" response that echoes back the requested object's contents (yes, this still happens).
  • IDOR + race condition. A transactional endpoint that checks ownership in step 1 and acts in step 3; concurrent requests change the ownership mid-flow.
  • IDOR + mass assignment. An object-update endpoint that accepts extra fields beyond what the frontend sends (role: "admin", tenant_id: 0) and applies them.
  • IDOR + cache deception. An IDOR that produces a personalized response, combined with a cache that stores it under a public-looking URL — exposes one user's data to everyone.
// Real-world chain · Kia web portal (2024)

Sam Curry and team disclosed an access-control chain in Kia's dealer/owner web portal where, given only a vehicle's VIN, an attacker could resolve the owner and remotely issue commands (locate, unlock, start) within seconds — bridging a web IDOR to physical-world impact across millions of vehicles. The takeaway: an ID you can read off a windshield became the key to someone else's car. Impact framing like that is what turns a "parameter swap" into a headline bounty.

→Second-order (stored) IDOR

The dangerous ID isn't always the one in your request — sometimes you plant a foreign ID in step 1 and the server dereferences it with elevated trust in step 2. The first request looks harmless and passes validation; the authorization gap only fires later, in a different context.

  • Stored reference. Set default_payment_id or avatar_file_id to a victim's object; the value is accepted now and rendered/charged later under your session — or theirs.
  • Async / job pipeline. Submit an export or report job referencing a foreign report_id; the worker runs with service-level privileges and never re-checks ownership.
  • Import / bulk endpoints. CSV/JSON import rows that carry an owner_id or org_id field the per-row handler trusts.

Test it by decoupling write from read: plant the foreign ID, then trigger the downstream action and watch whose data surfaces.

→Mass assignment overlap

Closely related to IDOR. The classic move: the frontend lets you edit name and bio; the API silently accepts role, email_verified, tenant_id, is_admin, or password_hash too. Always try adding fields the UI didn't send:

Mass assignment probePATCH
PATCH /api/users/SELF HTTP/2
Content-Type: application/json

{
  "name": "alice",
  "bio": "...",
  // fields the UI never sends — try them anyway
  "role": "admin",
  "is_verified": true,
  "tenant_id": 0,
  "subscription_tier": "enterprise",
  "credit_balance": 999999
}

→Race-condition IDOR

If the ownership check is non-atomic with the action, you can change ownership between them. Burp's Repeater → Send group in parallel (single-packet attack via HTTP/2) is purpose-built for this. The pattern: thread A transfers ownership of object X to your account; thread B reads X under the old owner's session. Hit them in the same TCP packet.

→WebSocket IDOR

Realtime apps (chat, collaborative editors, dashboards) push data over WebSocket. Authorization on the connection doesn't imply authorization on every message. Capture the WebSocket frames in Burp and try replaying with a different resource ID:

WebSocket message replayWS
# Connected as Account A. Replace document_id and re-send:
{
  "type": "subscribe",
  "channel": "document",
  "document_id": B's_doc_id
}

# If the server starts streaming B's doc updates → IDOR

→Mobile-backend IDOR

Mobile apps frequently expose endpoints the web app doesn't, with looser auth. Workflow:

  1. Pull the APK from an APK mirror, decompile with apktool + jadx
  2. Grep extracted resources for https:// base URLs and endpoint strings
  3. Pin-bypass with Frida or objection, proxy the live traffic through Burp
  4. Run the same two-account methodology against the discovered mobile endpoints

→Predicting "random" server-generated IDs

When an ID is minted server-side, its structure is often your way in — no leak required. The two that pay in practice (full mechanics and tooling in section 02):

  • UUIDv1 — timestamp + constant MAC/clock_seq. The sandwich attack brackets a victim token (e.g. a password reset) between two you generate and brute-forces the timestamps in between. Tools: guidtool, uuidtool, sandwich.
  • MongoDB ObjectID — one known same-process ID fixes the 40 "random" bits; you brute a narrow timestamp + small counter offset. Tool: mongo-objectid-predict.

UUIDv4 is genuinely random (2¹²² space) — abandon prediction, hunt for leaks. UUIDv7 / ULID / KSUID expose their creation timestamp but keep enough randomness to resist enumeration; their real weakness is being used where a secret was needed. Where prediction shines is token flows — password resets, email-verification, invite links — because there a predicted value is an instant account takeover, not just a read.

// What's not in this section

This guide does not provide step-by-step payloads for attacking specific real-world services. Every technique here is illustrative; apply them only on programs whose scope explicitly authorizes you to test. Out-of-scope testing is unauthorized access — different word, same legal class as the bug you're hunting.

→When to write a Python script

Once you've manually proven an IDOR on a single ID, the natural next step is to enumerate. Don't reach for Intruder — write a short script. It's faster to scope (don't run away with millions of requests), easier to make safe (limit to 5-10 records for the PoC, never dump the whole DB), and easier to attach to your report.

poc.py — safe IDOR enumeration sketchPYTHON
import requests

URL = "https://api.target.com/api/users/{}/profile"
TOKEN = "Bearer eyJhbGciOi..."  # your low-priv token

# Hard cap. NEVER dump the whole database.
SAMPLES = 5

for uid in range(7000, 7000 + SAMPLES):
    r = requests.get(URL.format(uid), headers={"Authorization": TOKEN})
    if r.status_code == 200:
        print(f"[+] uid={uid} email={r.json().get('email')}")
    else:
        print(f"[-] uid={uid} status={r.status_code}")
// Don't dump the database

A 5-10 record sample is enough to prove impact. Mass extraction is the line between "ethical disclosure" and "unauthorized access." Most programs explicitly forbid going past minimal PoC volume in their rules — and triagers will downgrade or close reports that obviously crossed it.

By 2026, AI is no longer a curiosity in the bug bounty stack — it's table stakes for top hunters. But it doesn't find IDORs for you. It collapses the time between "I have a hunch" and "I have a working PoC." Used carelessly it floods you with hallucinations and leaks target data to third parties. Used well it's a 3-5× force multiplier on the right phases.

→The multi-agent pattern (swarm auditing)

The most credible 2026 research direction isn't "one big agent finds bugs." It's many narrow agents that disagree. The open-source evilsocket/audit (built on the Claude Agent SDK, and inspired by 2025 industry research programs including Project Glasswing) is the clearest artifact to study — a multi-stage pipeline you can actually read:

Multi-agent vuln-discovery pipelineARCH
# Different models, deliberate disagreement, reachability gate

1. Recon      → Opus-class       // map the repo / API, emit Hunt tasks
2. Hunt       → Sonnet-class     // one attack class per agent (BOLA, BFLA, mass-assign…)
3. Validate   → Opus-class       // adversarial re-read, tries to DISPROVE
4. Gapfill    → Sonnet-class     // re-queue under-covered surface
5. Reachability → static analysis // gating step: is the buggy path reachable?
6. PoC        → Sonnet-class     // generate concrete exploit attempt
7. Triage     → Opus-class       // severity + dedupe
8. Report     → Opus-class       // structured writeup

The key insight: asking the same model to find AND validate a bug is a recipe for false positives. Different models at the Hunt and Validate stages catch each other's confabulations. The reachability gate kills the largest false-positive class — "this looks buggy in isolation but no real request path reaches it."

For solo hunters, the practical takeaway isn't running the full pipeline — it's splitting your AI workflow across two providers. Use one model to suggest IDOR candidates from an OpenAPI spec; paste the candidates into a different model and ask "argue why each of these is NOT vulnerable." The bugs that survive both passes are the ones worth testing manually.

// The 2025-2026 autonomous-agent reality

XBOW, an autonomous pentesting agent, reached #1 on HackerOne's US leaderboard in mid-2025 — proof that agents already find real, paid bugs at scale (BOLA/IDOR among them, since it's so pattern-driven). But keep the categories straight: XBOW and PentestGPT are offensive agents, whereas tools like ZeroPath are defender-side SAST — useful to understand, but not something you point at someone else's live target. For a solo hunter the edge isn't out-competing the agents on volume; it's the business-logic judgment they still lack.

→AI for PoC scripting

This is the workflow that genuinely shaves hours per finding. Once you've manually proven a single-ID IDOR, ask an LLM to scaffold the enumeration script — with explicit safety constraints:

Prompt template · safe PoC scriptingPROMPT
Write a Python script that demonstrates IDOR on this endpoint:

  GET /api/v2/users/{id}/profile
  Authorization: Bearer <token from env>

Constraints (NON-NEGOTIABLE):
- Hard-cap at 5 sequential IDs. Never more.
- Read TOKEN from env var, never hardcoded.
- Print only: id, http_status, length(response_body).
- Do NOT print response contents (could include real PII).
- Add a 1-second sleep between requests.
- Exit cleanly on any 429.

Output a single .py file. No commentary.

The constraints aren't optional — they keep your PoC inside ethical and legal bounds. The 5-record cap, the sleep, the no-content-print: these are the difference between "responsible disclosure" and "you exfiltrated PII." Most current LLMs will respect explicit caps if you state them up front.

→AI-generated reports

LLMs are excellent at structured writing — exactly what reports need. Workflow:

  1. Save the vulnerable request/response pair and your reproduction notes to a text file.
  2. Ask the LLM: "Write a bug bounty report using the structure: Summary / Severity / Steps to Reproduce / PoC / Impact / Remediation. Use the source material below. Do not invent details I haven't given you."
  3. Ask for a CVSS v3.1 vector with explicit reasoning per metric.
  4. Edit it. Triagers can spot LLM phrasing. The structure is fine; the voice should be yours.

→The caveats — where AI breaks IDOR hunting

// Data exfiltration to AI providers

If you paste a target's JS bundle or live HTTP traffic into a third-party AI provider, you have just transmitted target data to an unrelated third party. Many programs treat this as a scope/privacy violation. Always: (a) check whether the program prohibits AI use on their assets, (b) use a provider with no-training-on-data guarantees (Anthropic API, OpenAI's enterprise tier, Azure OpenAI with content-filter off), (c) avoid feeding live user PII into prompts. Strip and anonymize first.

// Hallucinated endpoints

The #1 LLM failure mode in recon: confidently inventing endpoint paths that "look" right for the platform but don't exist. Symptom: your fuzzer returns 404 across every "AI-discovered" path. Fix: always require the LLM to quote the source line where the endpoint appears, and verify the quote exists.

// False-positive flood

"Looks like an IDOR" from an LLM is roughly as reliable as "looks like an IDOR" from a junior pentester on day one. Without manually running the two-account loop, you'll generate noise that wastes program triage capacity and your own credibility. Confirmation is non-negotiable.

// The X03:2025 irony

The OWASP Top 10:2025 includes an honorable-mention category — X03:2025 Inappropriate Trust in AI Generated Code ("vibe coding") — explicitly calling out that developers shipping AI-generated code without review are now introducing the very access-control bugs we hunt for. Translation: the supply of IDORs is going up, not down. Modern AI helps the defenders write more code faster than they can review it; that surplus is your bounty pool.

→A recommended human-in-the-loop workflow

Integrating AI into the two-account methodology without breaking it:

The 2026 IDOR loop with AI inserted
  • Recon — LLM extracts endpoints from JS / OpenAPI / mobile decompile. You spot-check and prune hallucinations.
  • Triage — LLM ranks endpoints by IDOR likelihood given parameter shapes. You pick the top 10 to test.
  • Two-account loop — entirely manual. AI does not touch this step. Run Burp/Caido + Autorize as in section 03.
  • Bypass brainstorming — when manual hits 403, ask AI for "20 variants of this request to try." Run them yourself; don't trust AI's "this one works" claim.
  • Confirmation — entirely manual. Two screenshots, both accounts, real distinguishable data.
  • PoC scripting — AI scaffolds the script with hard caps. You read every line before running it.
  • Report writing — AI drafts to structure. You edit for voice and verify every claim against the actual evidence.

The pattern: AI compresses the boundaries of the workflow (recon → triage, finding → PoC, draft → report). The core authorization-reasoning step — where you actually decide a bug exists — stays human. That's the right division of labor in 2026, and it's likely to stay the right one through 2027.

// 09 · Closeout

Writing the Report

A good IDOR PoC writes itself. A great report frames the bug in business-impact terms, anticipates the triager's questions, and saves them the back-and-forth that delays payout.

→Report structure that gets paid fast

  1. One-sentence summary. "Authenticated users can read any other user's invoices by changing the user_id path parameter on GET /api/v2/users/:id/invoices."
  2. Severity claim with CVSS vector. Give your suggested CVSS but expect to negotiate. CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N for read-only horizontal PII = ~6.5 (Medium); add I:H and you're at High; cross-tenant or PII-at-scale and you're at Critical.
  3. Steps to reproduce. Numbered list. Include both accounts' setup, both tokens (redacted), the exact request, and the exact response. Don't make the triager assemble it.
  4. Proof of concept. Two screenshots minimum: (a) the legitimate request from Account B showing B's data, (b) the unauthorized request from Account A returning the same B data. If the PoC is a script, attach it but keep it ≤5 records.
  5. Impact. Quantify. "All 9,847 user IDs in the visible range return profile data including email, phone, real name, and onboarding answers." Mass exfiltration is what bumps the bounty.
  6. Suggested remediation. Brief. "Add a server-side check that request.user.id == params['user_id'] or that the requesting user has admin privileges on the target's tenant." You're not consulting; you're being polite.

→Scoring it: CVSS 3.1 and 4.0

Give a vector, not just a word. CVSS v4.0 (published Nov 2023) is now live on HackerOne (added March 2025) — and it fits IDOR better than v3.1, so learn to produce both. The upgrade that matters: v3.1's single Scope flag is replaced by two impact triples — VC/VI/VA (the vulnerable system) and SC/SI/SA (any subsequent system dragged in), which is exactly the shape of a cross-tenant breach. v4.0 also adds AT (Attack Requirements): AT:N for a trivial ID swap, AT:P when you first had to win a race or defeat a rate-limiter.

ScenarioCVSS 3.1CVSS 4.0
Horizontal read, full PII AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N → 6.5 Medium AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N
Cross-tenant read and write (SaaS) AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:N → 9.4 Critical AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:N/SC:H/SI:H/SA:N

Prefix each with the version tag (CVSS:3.1/… or CVSS:4.0/…). In the cross-tenant row, SC:H/SI:H is doing the persuasion — it states in the vector itself that a separate tenant's confidentiality and integrity fell, which a single S:C toggle could never articulate.

// Expect to negotiate PR and Scope

Triagers most often push back on two metrics. PR:L (you needed an account) — argue PR:N if the endpoint is reachable unauthenticated. And Scope / Subsequent-System impact — this is where cross-tenant and IDOR→ATO chains earn their Critical, so justify it explicitly rather than leaving it implied.

→Common triager pushback & how to pre-empt it

PushbackHow to head it off
"This is intended behavior — both users are in the same team"Test cross-tenant from the start. Show that different organization IDs leak too.
"You need the victim's UUID — that's not predictable"Show how you obtained the UUID from a public-facing endpoint, in your reproduction steps.
"This requires the victim's email"Show the email is harvestable from a sibling endpoint, OSINT, or a public profile.
"Low impact — just non-sensitive fields"Enumerate every field returned. Highlight anything PII, financial, or auth-adjacent.
"This is a duplicate"Cite your timestamps. Note any variant you found that the duplicate didn't cover.
"Out of scope"Re-read scope before reporting. If the endpoint is on a host marked in-scope, quote it.

→One-pager: the IDOR checklist

Print-and-tape-to-monitor edition
  • Two accounts live, both populated with distinguishable data (plus cross-tenant if the app allows it)
  • Burp/Caido + Autorize running; test three identities — owner, other user, and fully unauthenticated
  • Recon the surface — source maps (.js.map), archived URLs, Swagger/GraphQL, hidden params (arjun)
  • For every endpoint: swap the ID. Path, query, body, header, cookie, JWT claim.
  • For every endpoint: swap the method. GET, POST, PUT, PATCH, DELETE, HEAD, FOO.
  • Decode the ID first — base64? hashid? MongoDB ObjectID? UUIDv1? Predict before you enumerate.
  • For every blocked endpoint: path-normalization (slash, dot, encoding, extension) + header bypasses (X-Original-URL, X-Forwarded-For=127.0.0.1).
  • For every blocked endpoint: send the ID in two places (self in path, victim in body) + array/object/type-confused values.
  • For every UUID/random ID: hunt where it leaks publicly before giving up.
  • No data echoed? Check for blind IDOR via side effects and status-code oracles.
  • GraphQL? Fingerprint → introspection/Clairvoyance → aliased batch → nested fields → node() → fragments → mutations.
  • Found one? Check the chain — ATO, mass extraction, cross-tenant, mass assignment? Score it in CVSS 4.0.
